# knowledge-base
自分用の知識ベース＋AIに渡す前提の仕様書

各ディレクトリの意図
learning/

自分の理解を深めるためのメモ
雑でもOK、途中の思考も残す
「あとでAIに食わせて整理し直す」前提

specs/

AIや他人に渡す前提の“完成形に近い文書”
特に specs/ai/ は強力
→ 「このAIは何者で、何をしてよいか」 を明文化

snippets/

コピペ用・再利用前提
コードはここに集約すると検索性が爆上がり

logs/

学習日誌・思考ログ
「いつ何で詰まったか」が後で効く

rules/

このリポジトリ内でのルール
AIに渡すときの“癖”を固定できる


2. MDファイルを「AI前提」で書くコツ
① 見出しは「意味単位」で切る
Markdown## 目的## 前提条件## 用語定義## やりたいこと## やらないこと## 判断基準その他の行を表示する
→ この形、そのまま別AIに投げても高精度で理解される。

② 「決定事項」と「未決定事項」を分ける
Markdown## 決定事項- DBはSQLiteを使う- 認証は行わない## 未決定事項- デプロイ方法- ログの保存期間その他の行を表示する
👉 AIに「未決定事項だけ提案させる」使い方ができる。

③ 自分向けメモと仕様書を混ぜない

learning/ → 自分語りOK
specs/ → 感情・雑音を排除

これを分けるだけで AIの出力品質がかなり安定します。

3. MDファイルの「うまい活用方法」
活用①：AIに渡す「人格・役割定義」
Markdown# AI役割定義## あなたの役割- シニアWebエンジニア- 仕様の矛盾を指摘する## 口調- 端的- 日本語## やってはいけないこと- 推測で仕様を補完しないその他の行を表示する
👉 新しいAIに渡す最初の1ファイルとして最強。

活用②：プロンプトを「使い回す」
Markdown# コードレビュー用プロンプト## 入力- 対象コード- 目的## 出力形式- 問題点- 改善案- 修正版コードその他の行を表示する
→ プロンプトを資産化できる
→ モデルが変わっても再利用可能

活用③：GitHub × 検索 × 自分の脳

GitHubの検索はMDと相性が良い
repo:knowledge-base docker みたいに探せる
ObsidianやVS Codeとも連携しやすい


活用④：将来「公開 or 非公開」を切り替えられる

learning/ は非公開
specs/templates/ は公開

みたいに分けると、
あとからQiita・note・OSS化しやすい。
