# knowledge-base
自分用の知識ベース＋AIに渡す前提の仕様書
# Knowledge Base リポジトリ運用ガイド

このドキュメントは、学習メモ・仕様書・AI活用を前提とした GitHub リポジトリの設計思想と、Markdown（MD）ファイルの書き方・使い方をまとめたものです。

## ディレクトリ構成と意図

learning/  
自分の理解を深めるためのメモ置き場。雑でOK、途中の思考や迷いも残す。「あとでAIに食わせて整理し直す」前提。

specs/  
AIや他人に渡す前提の、完成形に近い文書。前提・制約・判断基準を明文化する。特に specs/ai/ は重要で、「このAIは何者で、何をしてよいか／いけないか」を定義する。

snippets/  
コピペ・再利用前提のコード集。ここに集約すると検索性が大きく上がる。

logs/  
学習日誌・思考ログ。「いつ・何をしようとして・どこで詰まったか」を残す。後から振り返ると一番価値が出る。

rules/  
このリポジトリ内でのルール置き場。Markdownの書き方、命名規則、AIに渡すときの癖を固定する。

## MDファイルをAI前提で書くコツ

見出しは意味単位で切る。

## 目的
## 前提条件
## 用語定義
## やりたいこと
## やらないこと
## 判断基準

この形は、そのまま別のAIに渡しても理解精度が高い。

決定事項と未決定事項を分ける。

## 決定事項
- DBはSQLiteを使う
- 認証は行わない

## 未決定事項
- デプロイ方法
- ログの保存期間

未決定事項だけをAIに提案させる使い方ができる。

自分向けメモと仕様書を混ぜない。  
learning/ は自分語り・感情・仮説OK。  
specs/ は事実・前提・制約のみ。  
これを分けるだけでAIの出力品質が安定する。

## MDファイルの活用方法

AIに渡す人格・役割定義。

# AI役割定義
## あなたの役割
- シニアWebエンジニア
- 仕様の矛盾を指摘する

## 口調
- 端的
- 日本語

## やってはいけないこと
- 推測で仕様を補完しない

新しいAIに渡す最初の1ファイルとして使う。

プロンプトの使い回し。

# コードレビュー用プロンプト
## 入力
- 対象コード
- 目的

## 出力形式
- 問題点
- 改善案
- 修正版コード

プロンプトを資産として蓄積でき、モデルが変わっても再利用可能。

GitHub検索との併用。  
repo:knowledge-base docker  
MarkdownはGitHub検索、Obsidian、VS Codeと相性が良い。

公開／非公開の切り替え。  
learning/ は非公開。  
specs/templates/ は公開。  
この分離により、Qiita・note・OSSへ転用しやすくなる。

## まとめ

このリポジトリは単なるメモ置き場ではなく、  
思考 → 構造化 → AI活用 → 再利用  
を回すための基盤。  
最初は完璧を目指さず、まず書いて、あとで整える前提で運用する。
