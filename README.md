# knowledge-base
自分用の知識ベース＋AIに渡す前提の仕様書

Knowledge Base リポジトリ運用ガイド
このドキュメントは、学習メモ・仕様書・AI活用を前提とした GitHub リポジトリの設計思想と、Markdown（MD）ファイルの効果的な書き方・使い方をまとめたものです。


ディレクトリ構成と意図
learning/
目的：自分の理解を深めるための学習メモ

雑に書いてOK
思考の途中経過・迷い・仮説も残す
「あとでAIに食わせて整理し直す」前提


自分の脳内ログをそのまま吐き出す場所




specs/
目的：AIや他人に渡す前提の、完成形に近い文書

感情や雑音を排除する
前提・制約・判断基準を明文化する
specs/ai/ が特に重要

このAIは 何者か
何をしてよくて、何をしてはいけないか
を明確に定義する。


snippets/
目的：コピペ・再利用前提のコード置き場

言語別・用途別に整理
検索性が非常に高くなる


「また同じコード書いてる」を防ぐ場所




logs/
目的：学習日誌・思考ログ

いつ
何をしようとして
どこで詰まったか
を記録する。


後から振り返ると一番価値が出るディレクトリ




rules/
目的：このリポジトリ内でのルールを固定する

Markdownの書き方
命名規則
AIに渡すときの癖・前提


AIとの共同作業を安定させるための土台




MDファイルを「AI前提」で書くコツ
① 見出しは「意味単位」で切る
## 目的
## 前提条件
## 用語定義
## やりたいこと
## やらないこと
## 判断基準



見出しごとに意味が完結している
そのまま別のAIに渡しても理解精度が高い


② 「決定事項」と「未決定事項」を分ける
## 決定事項
- DBはSQLiteを使う
- 認証は行わない

## 未決定事項
- デプロイ方法
- ログの保存期間



AIに「未決定事項だけ提案させる」使い方ができる
人間側の判断範囲も明確になる


③ 自分向けメモと仕様書を混ぜない

learning/ → 自分語り・感情・仮説 OK
specs/ → 事実・前提・制約のみ
これを分けるだけで、AIの出力品質がかなり安定する。


MDファイルのうまい活用方法
活用①：AIに渡す「人格・役割定義」
# AI役割定義

## あなたの役割
- シニアWebエンジニア
- 仕様の矛盾を指摘する

## 口調
- 端的
- 日本語

## やってはいけないこと
- 推測で仕様を補完しない



新しいAIに渡す最初の1ファイルとして非常に強力


活用②：プロンプトを「使い回す」
# コードレビュー用プロンプト

## 入力
- 対象コード
- 目的

## 出力形式
- 問題点
- 改善案
- 修正版コード



プロンプトを資産化できる
モデルが変わっても再利用可能


活用③：GitHub × 検索 × 自分の脳

GitHubの検索はMarkdownと相性が良い
例：
repo:knowledge-base docker



Obsidian / VS Code との連携もしやすい


活用④：将来「公開 / 非公開」を切り替えられる

learning/ → 非公開
specs/templates/ → 公開
この分離をしておくと、

Qiita
note
OSS
への転用が非常に楽になる。
